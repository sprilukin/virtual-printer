# Running virtual printers

```bash
.venv/bin/vp up brother-dcp-l1630w                      # loopback only, no mDNS
.venv/bin/vp up brother-dcp-l1630w duplex-color-laser-300dpi borderless-inkjet-letter --bind 0.0.0.0
```

- One printer per profile, ports from `--base-port` (default 6310; 8631 is the usual `ippeveprinter` port). `ipp://<host>:<port>/ipp/print` is printed at startup.
- `--bind 0.0.0.0` listens on the LAN and advertises each printer over mDNS (`_ipp._tcp`) with the profile's stored TXT record, the fake UUID and the `[VIRTUAL]` name. On loopback mDNS is off. `--no-mdns` turns it off anywhere. The Android emulator cannot see multicast: for it, print to `ipp://10.0.2.2:<port>/ipp/print` directly and use a physical phone for discovery.
- `--lenient` accepts jobs with unadvertised values (answers `successful-ok-ignored-or-substituted-attributes`); default is strict (`client-error-attributes-or-values-not-supported`). Per profile: `"options": {"validation": "lenient"}`.
- Ctrl-C (or SIGTERM) unregisters mDNS and closes the listeners.

## What a job leaves behind

`spool/<profile>/job-NNNN/`:

| File | Content |
|---|---|
| `document.pwg` | the raster as received (gunzipped if sent with `compression=gzip`) |
| `page-NNN.png` | one PNG per page; the unprintable margins are tinted red |
| `receipt.json` | sides, media, resolution, colour space, copies, page and sheet counts, pixel size, per-page raster details, job attributes as received, validation outcome, warnings |

Margins come from the job's `media-col` margins, else the profile's `media-col-default`. They are applied to the raster as delivered (no rotation).

A job is aborted (`document-format-error`) when the document cannot be decoded, or, in strict mode, when the raster resolution or type is not in `pwg-raster-document-*-supported`. The Brother advertises 600 dpi `sgray_8` only, so a 300 dpi raster to that profile aborts even though `printer-resolution-supported` lists 300.

Only PWG raster is decoded. Other document formats (URF, PDF) are stored as `document.bin` and the job is aborted with a warning in the receipt.

## Overlays

`profiles/<name>/overlay.json` = a base profile plus changes (`set`, `remove`, `dnssd_txt`, `dnssd_name`, `default_media`, `margins`, `options`). An overlay always gets its own UUID. The two shipped overlays are generated by `tools/make_overlays.py`.

## Control API

Each printer gets an HTTP+JSON control port, printed at startup: `--control-base-port` (default 7310, one per profile, same order as the printers). It has no authentication, so it listens on `127.0.0.1` unless you pass `--control-bind`; `--no-control` turns it off.

| Request | Does |
|---|---|
| `GET /state` | printer state (`idle`/`processing`/`stopped`), state reasons, active faults, job counts per state, known fault types |
| `GET /jobs` | every job received, with state and validation outcome |
| `GET /jobs/<id>` | one job plus its `receipt` once processed (and `error` if processing crashed) |
| `GET /jobs/<id>/pages/<n>.png` | the page image with margins shaded |
| `POST /fault {"type", "params"}` | switch a fault on (replaces the same type); `{"type": "busy", "enabled": false}` switches it off |
| `POST /reset` | forget all jobs, return faults to the profile's startup set |

```bash
curl -s -XPOST localhost:7310/fault -d '{"type":"busy","params":{"count":1}}'
curl -s localhost:7310/jobs/1 | jq .receipt.sides
curl -s localhost:7310/jobs/1/pages/1.png -o page1.png
```

## Fixed state

`options.state_reasons` (a list of keywords, e.g. `["toner-low-report"]`) is reported on every request; `options.printer_state: "stopped"` reports `printer-state=stopped` without any reason. Shipped overlays using them: `toner-low-only`, `stopped-no-reason`. The overlays `unsupported-no-raster`, `unsupported-150dpi` and `color-only-inkjet` change only capabilities.

## Faults

Startup faults go in the profile (or an overlay's `options`): `"options": {"faults": [{"type": "busy", "params": {"count": 1}}]}`. Request-level faults accept `count`: they fire that many times, then switch themselves off. Without it they stay on until cleared.

| Type | Params (default) | Behaviour |
|---|---|---|
| `busy` | `count` | Print-Job, Create-Job and Send-Document answer `server-error-busy` |
| `reset-mid-upload` | `after_bytes` (1024), `count` | the connection is reset (TCP RST) once a request body passes `after_bytes`; no job is created |
| `stall-body` | `after_bytes` (1024), `seconds` (until closed), `count` | the server stops reading the body, so a large upload stalls on a full socket buffer |
| `offline` | `seconds` (until closed), `count` | requests are accepted and never answered |
| `unauthorized` | `count` | IPP POSTs get HTTP 401 with `WWW-Authenticate: Basic` |
| `slow-completion` | `seconds` (5), `count` | each job stays `processing` that long before completing |
| `media-empty`, `media-jam`, `toner-empty` | `severity` (`error`; or `warning`, `report`), `job_mode` (`hold`; or `abort`) | `printer-state` becomes `stopped` and `printer-state-reasons` gets e.g. `media-jam-error`. New jobs wait in `processing-stopped` (`printer-stopped`) and finish when the fault is cleared; `abort` aborts them instead. Cancel-Job works on held jobs |

Notes: a stalled or offline connection is held until the client gives up, the optional `seconds` pass, or the printer stops. Get-Printer-Attributes is not affected by `busy`. `count` on `reset-mid-upload`/`stall-body` is used up by the first request that exceeds `after_bytes`, so small probes in between do not consume it.

## TLS and Basic auth (`ipps-auth-office`)

`vp up ipps-auth-office` serves `ipps://` (TLS 1.2+ from connect, same port scheme as `ipp://`) and requires HTTP Basic auth on every IPP POST: user `office`, password `print-me`. Without valid credentials the answer is `401` with `WWW-Authenticate: Basic realm="Office printer"`. A plain `GET /ipp/print` info page stays open. It advertises `_ipps._tcp` with `TLS=1.2` and `air=username,password`, and `uri-security-supported=tls`, `uri-authentication-supported=basic`.

Certificates live in the gitignored `tls/` directory and are reused across runs while they still cover the needed names (`localhost`, `127.0.0.1`, `10.0.2.2` for the Android emulator, the `--bind` address or the LAN addresses, plus any `--tls-san`).

| Mode | How | Use |
|---|---|---|
| `self-signed` (profile default) | `tls/<profile>/cert.pem` | the client pins this one file, or you test that it refuses an unknown cert |
| `ca` | `vp up ipps-auth-office --tls-mode ca` | install `tls/ca/ca.pem` (print its path with `vp ca`) as a trusted CA on the test device once; every profile is then trusted |
| `files` | `"tls": {"mode": "files", "cert": "...", "key": "..."}` in a profile's `options` | bring your own cert (paths relative to the repo root) |

Profile options: `"options": {"tls": {"mode": "self-signed"}, "auth": {"type": "basic", "realm": "...", "users": {"name": "password"}}}`. Either can be used alone. `GET /state` on the control API shows `tls`, the user names (never passwords) and `auth_failures`. The `unauthorized` fault still works on plain profiles to exercise the 401 path without TLS.

```bash
curl --cacert tls/ipps-auth-office/cert.pem -u office:print-me https://localhost:6310/ipp/print
```

Android: a user-installed CA is only trusted by apps that opt in through their network security config. The emulator reaches the host at `10.0.2.2`.
